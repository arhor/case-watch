# Startup configuration

`case-watch` reads environment variables (it does not load `.env` files). Startup validates syntax and permissions, the database schema, and stored credentials before starting Telegram polling or background work. See [service lifecycle](operations.md).

Two values are required: `CASE_WATCH_TELEGRAM_BOT_TOKEN` and `CASE_WATCH_DB_PATH`. Token syntax is a positive decimal bot identifier, a colon, and 35 ASCII letters, digits, underscores or hyphens. Local syntax validation does not verify Telegram acceptance. After local storage validation, startup checks acceptance with a context-cancellable `getMe` request bounded to 15 seconds; any failure prevents startup. Runtime token rejection stops the service; correct the environment and restart normally. The database path must be nonblank and contain no NUL/newline. It is preserved as supplied; a relative path resolves against the process working directory. No default silently chooses a storage location.

Every ordinary private-chat user can use the bot. There is no user allowlist or access-mode configuration. Existing `CASE_WATCH_ALLOW_ALL_USERS` and `CASE_WATCH_ALLOWED_USER_IDS` environment values are ignored and can be removed from operator settings.

See [the synthetic example](../.env.example). Diagnostics identify invalid variables without printing supplied values. Never print configuration structs, token values, credential input, or raw adapter errors. The database directory must have no group/other permissions; existing database files must be regular mode-0600 files without symlinks or extra hard links. Portal credentials are stored as plaintext in SQLite during WIP development, so access to the database file grants access to them. Backups remain deferred under ADR 0008.

The Telegram entry point accepts only a non-bot sender with positive matching sender/chat IDs in an ordinary private chat. Commands bind ownership to this transport identity; users cannot supply a different owner ID. Tracking and storage preserve owner-scoped access and enrollment identity fencing. Scheduled checks and notifications process all enrolled owners subject to existing cooldowns, removal, blocked-recipient and delivery gates. See [ADR 0017](adr/0017_remove-user-authorization.md).
