# Independent implementation audit

2026-11-01. This review covers the product contract and all accepted ADRs, including the no-backup and confirmed-removal amendments. It reviews production code and offline tests, rather than treating a passing suite as proof of every requirement. No live portal/Telegram requests, capture reads, real keys, deployment, backups or target-device execution are part of this audit.

## Findings identified and corrected

| ID | Severity | Finding and reproducible trigger | Required regression evidence |
| --- | --- | --- | --- |
| A1 | P2 | `telegram.reply` performs `DirectGate`, `Send` and `DirectOutcome` as separate operations. Async enrollment confirmations can overlap intake replies and the durable worker. Pause a direct reply after its gate check, let another send persist a 429/401 global gate, then release the reply: it still sends. `notifications.Worker.send` serializes durable sends only. ADR 0009 requires reported global gates to suppress outbound sending across recipients. | Use one shared admission/send/outcome critical section for direct and durable messages. A queued reply must recheck the persisted gate after an active send reports a rate/token failure and must make no API call or queue acknowledgement. |
| A2 | P2 | A structured rate/token failure from a direct send can be lost when the intake context is canceled before its outcome is saved. `RecordDirectOutcome` derives its timeout from that canceled context; service wiring deliberately ignores the resulting error during cancellation. Restart therefore lacks the required persisted gate. The existing graceful-cancellation test checks only the process result, not the reopened gate. | Cancel between the structured send outcome and persistence; verify bounded cancellation-independent persistence, then reopen SQLite and assert the rate deadline/token suspension. Actual persistence failure must remain visible. |
| A3 | P2 | A valid explicit unblock is ignored unless a block was already recorded locally. `Worker.events` maps both `Unblocked` and ordinary `Interaction` to `SetBlocked(false)`, whose `onlyBlocked` path returns without recovery when the stored blocked bit is zero. Exhaust a head, miss the block update, then observe a valid Telegram old=banned/new=member update: the queue stays exhausted. Such an update itself proves the block/unblock cycle; ADR 0009 permits recovery on that evidence while forbidding recovery from an unrelated interaction. | Distinguish explicit unblock evidence from interaction fallback. Verify explicit unblock resets only the oldest unsent cycle while preserving lifetime counts/order/global gates without a stored block bit; an ordinary interaction must leave permanent/exhausted pauses intact. |

All three findings were corrected and independently re-reviewed. `Worker.SendDirect` now holds the same mutex as durable sends across gate admission, the single raw transport attempt and global-outcome persistence. Known 429/401 outcomes persist through a bounded context independent of cancellation; real persistence failure becomes `ErrWorker` and service failure even during shutdown. `ResumeUnblocked` applies explicit authenticated unblock evidence independently of the locally stored blocked bit; ordinary interaction retains the narrower proven-block fallback.

New worker tests cover a direct reply waiting behind a rate-limited durable send, a canceled direct rate/token outcome gating queued durable work and surviving reopen, fatal persistence failure, and explicit unblock after a missed block event while interaction leaves the permanent pause intact. New service tests reopen the database to verify canceled direct rate/token outcomes, and inject actual gate-write failure to verify process failure. The corrected code and these assertions were reviewed independently; no open code defect remains from this audit.

## Verification and remaining acceptance

The parent independently ran fresh `go test -count=1 -race ./...`, `go vet ./...`, a CGO-disabled Linux ARM64 build/static ELF inspection and `git diff --check`, all with exit 0 before this review. Step 12 records ordinary/full race runs and synthetic `docker compose config --quiet` exit 0.

After reviewing remediation, this auditor independently ran `source "$NVM_DIR/nvm.sh" && nvm use && GOCACHE=/private/tmp/case-watch-go-build GOMODCACHE=/private/tmp/case-watch-go-mod GOPROXY=off GOSUMDB=off go test -count=1 -race ./internal/notifications ./internal/telegram ./internal/storage ./internal/service && git diff --check`: exit 0, all four packages passed. This is fresh focused verification of the corrected interleavings and recovery behavior; final whole-repository verification is recorded by the parent separately.

The parent subsequently reran the full repository after all remediation: ordinary tests, race tests, vet, and `CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build -trimpath -o /private/tmp/case-watch-final-arm64 ./cmd/case-watch`, followed by static ARM aarch64 ELF inspection and whitespace checks, all exit 0. See [implementation progress](implementation-progress.md) for the final command record. ADR checklists now link to this evidence; literal commit tasks, conditional browser fallback, deferred backup composites, unsupported shared-association behavior and live/Docker/Pi composites remain unchecked rather than overstating completion.

Docker's daemon was unreachable. Image build and actual non-root permissions, named-volume ownership copy-up, key bind-mount access, CA trust, embedded timezone behavior, recreation preserving encrypted state/history/cooldowns/queues/gates, normal/forced termination, restart policy and host-boot behavior have not been demonstrated. They remain environment acceptance work, separate from code findings. No composite Docker criterion is passed by cross-compilation or Compose parsing alone.

Repeated live authentication/session renewal, portal-display comparison, real bot behavior, execution on the Pi, idle/peak memory/check-duration measurements, host workload inventory and an agreed Pi resource budget remain outstanding. This implementation task does not authorize those activities or establish deployment suitability. Backup/restore criteria in ADRs 0004/0006 are deferred by ADR 0008, not silently passed.
