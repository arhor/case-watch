# Credential encryption and key provisioning

ADR 0006 selects field encryption; database metadata stays readable. A loaded `internal/credentials.Keyring` seals the number and password together using AES-256-GCM with `cipher.NewGCMWithRandomNonce`. The standard library prefixes a random 12-byte nonce and adds a 16-byte authentication tag. Use fewer than 2^32 encryptions per key. JSON-array AAD binds the application purpose, encryption format version, key ID and immutable destination enrollment ID. Storage must supply the destination identity to `Open`, never copy an identity from a different record with its payload. Authentication failures return no credentials and generic errors.

The keyring JSON has exactly `version` (integer 1), `active_key_id` (nonempty string), and `keys` (object mapping nonempty IDs to standard padded base64 encoding of exactly 32 bytes). Unknown members, duplicate object members (including duplicate IDs), malformed JSON, trailing documents and unsupported versions are rejected. Keys load into process memory; file changes take effect on restart.

Provision explicitly, before startup, with `case-watch provision-key /absolute/protected/keyring.json initial`. First create a private directory outside this repository and outside the SQLite directory/volume, owned by the service account with mode `0700`. This action creates a random key in a mode `0600` file, prints no key, and refuses to overwrite any existing entry. It requires no bot configuration and creates no directories. A failed write/sync can leave an incomplete file; inspect and resolve it explicitly, never automatically replace an existing key. Keep `CASE_WATCH_KEY_FILE` pointing to this persistent file; a container receives it through a separate read-only mount.

Loading requires a regular, non-symlink file with exactly mode `0600` and a containing directory with no group/other permissions. The final directory cannot be a symlink. Ancestor directories must be trusted operator-controlled paths. Directory validation and file access use a pinned directory root; loading rejects special files without blocking. Configure the service account ownership explicitly. Keep keys away from database files and the repository; this adapter cannot infer those deployment paths.

The service loads the existing keyring, enforces configured path separation, and authenticates every existing credential record before enabling network work, including records belonging to currently unauthorized users. Startup never calls provisioning, replaces missing keys, resets records or interprets authentication failure as portal-password rejection. Enrollment seals credentials before the atomic baseline commit. Plaintext exists transiently in Go memory; clearing temporary byte slices does not guarantee erasure of all historical copies.

Rotation is explicit stopped-service maintenance: `case-watch rotate-key DB_PATH KEY_PATH NEW_ID`. It persists old and new keys with the old active ID, re-encrypts all records transactionally using their existing identities and fresh nonces, verifies committed records, and then persists the new active ID. Atomic replacement and file/directory synchronization protect keyring writes. Keep the old keys; automatic retirement is not implemented. After interruption, retry with the same inactive new ID to reuse its persisted key. See [operations](operations.md) for recovery and locking. No backup/restore tooling or copies are introduced under ADR 0008's amendment. Key or storage loss can require re-enrollment and loses local history/pending transitions. Full host compromise or possession of both database and key can reveal credentials.
