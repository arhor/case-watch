# SQLite storage foundation

`internal/storage` implements ADRs 0004–0006 using pinned `modernc.org/sqlite` v1.61.1 and `database/sql`. `Open` requires an existing service-owned parent directory and opens one serialized connection with foreign keys, DELETE rollback journaling, FULL synchronization and a 5-second busy timeout. Keep the configured database path on local persistent storage and restrict its directory to the service account. Database files and journals are excluded from Git. SQLite metadata, stages and owner IDs remain readable; only credentials are encrypted.

Fresh databases initialize through golang-migrate v4.20.1 and embedded SQL. The consolidated initial schema is version 1 in schema_migrations; PRAGMA user_version remains zero. Legacy databases are rejected without conversion or reset. Dirty, malformed and unsupported metadata prevent startup. Add immutable sequential migrations under internal/storage/migrations as .up.sql files. Each SQL migration is transactional, while version/dirty markers commit separately. No downgrade command or automatic force is provided. Backups remain deferred under ADR 0008.

Allocate an opaque `NewEnrollmentID`, seal transient credentials using the credential adapter and that ID, then call `Enroll` with the authenticated owner and successful portal baseline. One owner can have one enrollment. The credential ID, ciphertext and baseline commit together, with no baseline notification. The identity registry prevents identity reuse and survives explicit removal. Read methods reconstruct the credential ID from its destination row for AAD verification. The service authenticates all stored records before networking; storage does not hold encryption keys or accept plaintext credentials.

`Observe` applies owner and enrollment identity predicates, compares the current stage, and commits cache/time, transition history and durable pending notification together. Unchanged stages refresh only successful-check time. Transitions are individual occurrences with monotonically increasing sequence IDs; A → B → A retains both changes and both queued records. The single recipient is the enrollment owner under the product's current one-case model. A failed transaction leaves the earlier cache and queue unchanged. Callers perform portal and Telegram requests outside these transactions. Storage errors expose fixed categories, never raw driver errors or supplied data.

`Enrollment` is owner-scoped. `Enrollments` is a trusted startup/background inventory: consumers must authorize before decryption or work. `History` requires owner and enrollment identity. No SQL or driver values escape these APIs. Current startup authorization is still enforced by callers; owning a row alone does not authorize work.

Step 5 extends the foundation with durable cooldowns, attempt reservation, recipient/global gates, delivery outcomes and explicit confirmed removal as documented below. Pending work remains durable across reopen; no current runtime worker invokes these APIs or sends notifications.

Offline tests use temporary databases and synthetic AES-GCM credentials, exercising atomic failure rollback, repeated stages, concurrent observations, reopen, ownership, ciphertext binding, plaintext exclusion and concrete connection settings. No live portal or Telegram requests are involved.

## Runtime and maintenance storage (step 5)

The consolidated initial migration includes runtime state. Legacy v1/v2 databases are rejected. `ReserveCheck(owner, enrollment, manual, now)` atomically persists case and optional user attempt-start guards, with eligibility at exactly 60 seconds. Failed checks consume reservations; cache reads and joins must skip reservation. The tracking coordinator owns in-process in-flight joining and successful-cache freshness, and must prevent overlapping checks even if one lasts over 60 seconds. `Remove(owner, enrollment)` atomically cascades enrollment, case guard, history and queue deletion, while retaining the immutable identity registry, user manual guard, recipient pauses and global gates. Callers must cancel/drain first; late observations and delivery acknowledgements fail against removed identities.

`Queue` exposes ordinary-value delivery metadata in global enqueue sequence order for one recipient, including delivered rows and confirmed message IDs. `ReserveDelivery` reserves only the oldest outstanding record, increments cycle/lifetime counts before network access, and enforces recipient pauses, global token suspension and rate deadline. Its returned sequence/enrollment/lifetime tuple is the completion token; stale completions cannot acknowledge a newer attempt. `CompleteDelivery` commits sanitized outcome, backoff, message ID and gates together. Delays are 30/60/120/240/480 seconds measured from completion, with rate-limit minimums. The sixth failure retains the head and pauses the recipient; later records cannot overtake it. No network call occurs inside storage. Authorization suppression belongs to the worker and must occur before reservation, without consuming an attempt.

Startup calls `RecoverDeliveries(now)` once before starting workers. Reserved attempts become `uncertain` failures, retaining counts and applying backoff from recovery time (or pausing an exhausted cycle). Never call recovery while sends are active. `ResumeRecipient` is explicit operator recovery after correction: resets only the oldest outstanding cycle and deadline, preserving lifetime counts and global gates. `SetBlocked(true)` records block evidence; `SetBlocked(false)` resumes only when block evidence exists, so unrelated private interactions cannot clear exhaustion/permanent pauses. `ResumeUnblocked` applies explicit authenticated unblock evidence even when the earlier block update was missed. Resume operations reject active reservations. **The notification coordinator serializes membership updates/recovery with recipient sends and retains interrupted events for retry.** Never drop that event or reset an active attempt. `ResumeToken` is explicit correction recovery and leaves rate deadlines intact. These are maintenance/storage APIs, not Telegram administrator commands; the worker and stopped-service maintenance entry points are implemented.


Step 7 adds `CheckEligibility(owner, enrollment, manual)`, a read-only lookup of persisted attempt-start deadlines. It enforces the same owner/identity predicates without creating/updating guards, allowing cached status replies to explain eligibility without reserving work. The shared tracking coordinator now consumes these storage APIs; see the step 7 handoff in [implementation progress](implementation-progress.md) for the required removal/send/membership gate and the distinction between cached provenance and successful-cache age.

Step 9 adds `DeliveryHeads`, an ordinary-value oldest-outstanding inventory per recipient, and fenced `ReleaseDelivery` for a reserved attempt that provably never reached the network. Release restores attempt counters; it must never follow a send or uncertain acceptance. `RecordGlobalOutcome` applies direct-reply token/rate failures without acknowledging durable work. The notification worker calls startup recovery before sending, serializes sends and membership via the tracking owner gate, and drains bounded outcome persistence before removal deletes rows. Completion persistence failures stop the worker; restart recovery handles the uncertain reservation rather than leaving it silently stuck.
