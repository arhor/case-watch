# Telegram adapter handoff

`internal/telegram.New` pins ADR 0003's library v1.27.0 and creates no network requests (`WithSkipGetMe`). The service validates configuration, keys and every stored credential, then calls `Validate(ctx)` before recovery or workers start. Validation uses a context-cancellable `getMe` request bounded to 15 seconds. Any error prevents startup; only structured unauthorized errors are classified as token rejection. Use one adapter/poller per token; stop the context and wait for Start before closing tracking/storage. Start cancels polling, drains library intake and enrollment goroutines, and clears drafts on shutdown. `Close` is also available for offline/manual use after stopping intake. Do not call Close concurrently with starting new intake.

Config injects the shared auth policy, coordinator, ciphertext-only enrollment reader, clock, optional HTTP client/endpoint, sanitized diagnostic callback and optional membership callback. Ordinary `Membership` values identify authenticated private owner evidence: explicit block/unblock and incoming interaction. The service connects this callback to delivery recovery, which serializes it with recipient sends, respects context cancellation, and preserves permanent/exhausted pauses without block evidence. The synchronous callback must not run an outbound send or wait indefinitely: command intake, including removal, follows it. The service owns the delivery worker's lifetime.

`Send` implements application.Sender as one API attempt with sanitized outcome/error. It distinguishes definite blocked description from other forbidden errors; structured unauthorized, rate-limit and permanent API errors map separately. The durable worker owns retries and rate gates under [ADR 0013](adr/0013_keep-telegram-send-cooldown-in-memory.md) and the token rejection policy in [ADR 0012](adr/0012_fail-fast-on-invalid-telegram-token.md). Replies and deletion attempts have no application retry. Plain text is sent without parse mode; portal stage text is preserved. Library debugging is disabled and raw errors never reach diagnostics.

Library intake runs in update order. Enrollment runs asynchronously so `/cancel` can cancel the coordinator check; subsequent `/enroll` asks the user to wait for that work to finish. Status/removal run synchronously. Drafts hold only the number, never a retained password; inactivity expires at the exact ten-minute deadline. A minute sweep clears idle expired plaintext, and each incoming message checks exact deadlines. Confirmation expires ten minutes from its prompt. Restart discards both. Go reference clearing is not secure memory erasure, and best-effort Telegram deletion does not guarantee platform-copy deletion. No incoming command durability or exactly-once semantics are claimed.

Offline tests inject an in-memory HTTP transport through the real library. They never contact Telegram or the portal. Service startup, persistent delivery and maintenance are implemented and tested separately; live bot validation and target-device behavior remain unverified.

Delivery integration: `Config.DirectSend(ctx, owner, text)` applies only to direct command replies and is wired to `notifications.Worker.SendDirect`. It serializes gate admission, the send and in-memory cooldown updates with durable sends. Known rate-limit outcomes update the shared in-memory deadline even if intake is canceled. Positive retry_after is honored; otherwise the cooldown is 30 seconds. Restart clears the shared cooldown, while queued notification retry deadlines remain durable. Invalid-token send outcomes stop the worker and service. Structured unauthorized errors during polling or credential-message deletion emit `telegram_invalid_token`, which the service treats as fatal. Raw `Adapter.Send` remains the one-attempt transport primitive, preventing recursion. Direct replies never acknowledge notification rows. Map `Membership` fields to ordinary `notifications.Event` and call `Worker.Membership`; explicit unblock evidence can resume a cycle even if the earlier block update was missed, while an ordinary interaction only clears a known block. Events interrupted by removal/cancellation remain queued for the next worker step. Start delivery recovery before incoming polling. Recovery depends on observed evidence and is not guaranteed after arbitrary downtime.
